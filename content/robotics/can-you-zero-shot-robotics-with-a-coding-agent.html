Here is a robot that can’t reach a radio. It can see the radio 1.91 m away, and it knows how to grasp it, but every call to navigate_to_pose comes back PLANNING_ERROR. The goal pose it keeps picking sits about 20 cm from the edge of a table, inside the planner’s collision margin, so the planner refuses. The robot is run by a coding agent (Claude Code or Codex) that writes Python on top of hand-built perception, grasping and motion-planning functions. Nobody is going to train a robot policy to fix this, and the pretrained language model behind the agent gets no weight updates. Its weights will be exactly the same tomorrow. So how is it supposed to get better?

ASPIRE, from NVIDIA GEAR and collaborators at Michigan, UIUC, Berkeley and CMU, gives an almost embarrassingly simple answer: write the fix down. When the agent works out a repair, the repair becomes a few lines of Markdown that say what the failure looks like, when the fix applies and what to do. A second agent checks that the note works on its own, and every later task gets to read it. Let’s fix the radio problem first: try another approach angle, keep the first one the planner accepts, and write down when to use that trick.

How far can this get? With Claude Opus 5.5 allowed to debug each task, the later manuscript reports an average success rate of 99% across 80 simulated LIBERO-Pro tasks. The transfer test in step 5 is stricter: old notes, and no debugging on the new task. The model also matters enormously, even with no saved notes at all. Keep the robot’s tools and setup the same, turn search off, change only the language model, and success jumps from 14.8% with GPT-6 Luna to 99.2% with Claude Opus 5.5. (Every model gets the same 10 LIBERO-Pro Goal tasks with shifted object positions, each scored on 50 starting arrangements it never saw while debugging.) For weaker models, it helps a lot to show the agent what went wrong and let it try several programs. With Opus 4.6, logging every primitive call (step 1) lifted the LIBERO-Pro average from 14% to 62%, and search, which writes several candidate programs and scores them on development seeds, took it to 72%. On LIBERO-Pro Object, Goal and Spatial, search changes success by at most 2 percentage points for Opus 5, GPT-6 Astra and Opus 5.5.

So is this Sutton’s bitter lesson reaching robotics? Jim Fan frames it that way, and I can see the appeal: changing the model produces a huge gain while the robot’s tools stay the same. But people still wrote those tools, along with the prompts, the curriculum and the rules for admitting a note, and this experiment does not tell us whether they will eventually become unnecessary. The available API bounds what a program can do. Generated programs check results between blocking motion calls like move_to_pose, on a scale of seconds, while a hand-built controller tracks position targets underneath. Fast dynamics are untested, and so is whether the agent could write that faster feedback layer itself. Still, I buy the mechanism. If your robot runs on a coding agent, store each repair as a note with the failure signature, the conditions where it applies and the fix, and make a fresh agent prove it can follow the note. That gives you a robot that keeps adapting while its model weights stay frozen.

The navigation repair as code (an abbreviated sketch of the rule in the paper’s Appendix A):

if status == 'PLANNING_ERROR' or distance_to_target > 1.0:
    for angle in [0, 90, -90, 45, -45]:
        goal = obj - dist * rotate(unit, angle)
        if navigate_to_pose(goal).ok:
            break

The released notes live in .claude/skills/iterative-debugging/skills/ (grasp.md, localize.md, transport.md, manipulation.md) at commit fa00f0e. They mix starting templates with entries that runs added, and the file doesn’t say who wrote each line. One entry in grasp.md is a good example of API knowledge a model can’t guess. close_gripper() treats a stall against the object as a successful close, returns ok=True and updates the recorded commanded state. set_gripper(0.0) during a grasp can time out and leave a stale open command behind. The two calls look the same and act differently. The paper reports these skill categories, which emerged during runs and were not defined in advance: localization, prompt refinements, grasp heuristics, navigation recovery, motion primitives and debugging routines.

Search, simplified from the paper’s Algorithm 1:

history = [(p0, dev_score(p0), trace(p0))]
for round in 1..R:
    write K programs from (task, skill store, best 3 in history + traces)
    score each on development seeds; add to history
    if best score >= τ: stop
extract validated patterns into the skill store
run the best program once on the unseen seeds

The score is s̄ = (1/T) Σt=1..T (1/S) Σs=1..S 1[success(t, s)], with T = 10 tasks and S = 50 unseen seeds. Each seed fixes the object layout, the distractors and the initial conditions. After the curriculum, the coordinator revisits low-scoring tasks one more time with the complete library.

Where the language model sits: finished LIBERO-Pro and Robosuite programs run with no more model calls. BEHAVIOR-1K generates successive code blocks from the current traces. The cube deployment has the model issue individual actions, so model latency stays inside some control loops.

Security: the generated Python can import anything, according to the repository warning. Run it on an isolated machine.
